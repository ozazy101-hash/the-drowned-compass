Research date: 2026-10-09. **Decision proposal, not deployment approval or hosting proof.** Read-only primary-source research; no account, credential, image pull, dependency installation, provisioning, paid provider call or hosted change performed. ## Concrete option

Use **AWS Lambda, Node 24, ARM64**, solely for authoritative image decode, bounded normalization, exact masked composition, lossless PNG encoding and private provisional upload. AWS lists `nodejs24.x` on Amazon Linux 2023, with retirement scheduled for April 2028. This is an officially supported runtime path rather than an assertion that the retained probe already runs successfully there. [AWS Node runtimes](https://docs.aws.amazon.com/lambda/latest/dg/lambda-nodejs.html).

Proposed initial configuration: 2048 MB memory; 60-second function timeout; 512 MB `/tmp`; reserved concurrency 1 after approval/proof, otherwise 0; no provisioned concurrency, event queue or automatic invocation retry. These are selected trial limits, not measured performance. Lambda supports memory-dependent CPU allocation, configurable timeout and temporary storage; synchronous request and response payloads are each limited to 6 MB. [AWS quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html). Reserved concurrency imposes an execution ceiling; setting it to zero disables processing. Account availability must be checked: reservation rules retain 100 unreserved units, and new accounts can have reduced quotas. [AWS concurrency configuration](https://docs.aws.amazon.com/lambda/latest/dg/configuration-concurrency.html).

Begin proof at the actual 1024×1024 retained corpus. Trial worker admission: PNG only, each encoded input/output at most 20 MiB, each edge at most 1024 and at most 1,048,576 decoded pixels; reject mismatched dimensions and extra frames. Frame validation is a **future worker proof requirement**: the current probe decoder ignores APNG `acTL`/`fcTL`/`fdAT` chunks, so unchanged replay proves pixel behavior only, not APNG rejection. Descriptor body at most 32 KiB; bounded fetch/upload and total internal deadline 50 seconds to leave timeout headroom. An operator must explicitly choose a larger ceiling only after measurement. The 16-million-pixel upload allowance is **not** an accepted generation/composition deployment ceiling. The provider's own bounds remain separate and continue to apply before paid submission. These limits are engineering proposals derived from the retained corpus, not AWS guarantees.

## Module placement and small interface

Place the image worker adapter behind the existing owned server generation seam. PartyContent transport, DM authorization and workspace observation remain unchanged. Ticket06 remains the **sole** owner of request/job identity, provider submission, usage, quotas, spend reservations, cancellation, reconciliation and atomic ticket04 attachment. The worker has no database ledger, provider key, Supabase service-role key or presentation-selection operation.

One internal operation is sufficient:

```text
verifyArtwork({requestId, jobId, parentVersionId?, expiresAt,
  source?: {objectIdentity, sha256, bytes, width, height, downloadUrl},
  candidate: {objectIdentity, sha256, bytes, width, height, downloadUrl},
  region?: {x,y,width,height}, output: {objectIdentity, uploadCapability},
  provisionalOutputToReverify?: {objectIdentity, sha256, bytes, downloadUrl}})
  -> {requestId, jobId, parentVersionId?, sourceSha256?, candidateSha256,
      outputObjectIdentity, outputSha256, encodedBytes, mime, width, height,
      region?, comparedOutsidePixels?, changedOutsidePixels?, codecVersion}
```

This is a proposed normalized interface, not a second production contract implementation. Whole-map candidates use validation/normalization; constrained revisions additionally require saved-parent source and region. Its depth hides image parsing, bounds, fetch restrictions, exact pixel invariants, encoding and receipt verification in one module. Callers learn one intent and explicit outcomes: invalid input, expired capability/deadline, resource bound, storage failure, or uncertain transport outcome.

Hidden invariants: verify SHA256 and actual bounded byte count before trusting image metadata; decode and confirm canonical dimensions; reject arbitrary resizing/outpainting; compare and compose in one explicitly defined canonical RGBA decoder representation. Copy selected candidate pixels into source bytes, rather than alpha-blending the entire candidate. Re-decode the final lossless PNG and require zero changed decoded pixels outside the selected rectangle and exact selected candidate pixels. Preserve source geometry and registration only when ticket06 validates the trusted receipt against its saved parent and ticket04 canonical document/placement. Integrity digest does not establish registration. Changing codec/canonical color or orientation policy requires new compatibility proof; current PNG probe semantics are the baseline.

## Auth and private object transport

Configure a Function URL with **AWS_IAM**, never `NONE`. Ticket06's owned server signs requests with SigV4; browsers receive neither invocation credentials nor private capabilities. [AWS SigV4 invocation](https://docs.aws.amazon.com/lambda/latest/dg/urls-invocation.html). The invocation principal needs **both** `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` for the exact function/alias; restrict with `lambda:FunctionUrlAuthType=AWS_IAM` and `lambda:InvokedViaFunctionUrl=true`. Cross-account invocation additionally needs the appropriate resource policy. [AWS Function URL permissions](https://docs.aws.amazon.com/lambda/latest/dg/urls-auth.html). Secret provisioning/rotation for this narrowly scoped caller identity is a deployment prerequisite; it is not assumed available. Prefer temporary credentials if a supported federation path is established; do not silently substitute long-lived broad credentials.

The 6 MB synchronous ceiling makes combined base64 source/candidate payloads unsuitable: two individually valid images can exceed it. Send only bounded JSON object descriptors. Ticket06 creates signed private **download** URLs with a proposed 120-second TTL; Supabase accepts an expiration in seconds. No image transformations are requested. [Supabase signed downloads](https://supabase.com/docs/reference/javascript/storage-from-createsignedurl).

For output, ticket06 supplies a path-scoped signed upload capability for a unique private provisional job/request path with `upsert:false`. Supabase's standard signed upload capability lasts **two hours**, not 120 seconds, and works without further authentication. [Supabase signed uploads](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl). Therefore a 120-second acceptance deadline is application enforcement, not token revocation. A shorter upload-token lifetime would require a separately designed owned relay; it is outside this option. Never log capabilities, signed query strings or authorization headers.

Worker validation must allow only the configured exact Supabase HTTPS hostname, bucket and normalized object paths matching the descriptors; disallow redirects, URL credentials, non-HTTPS URLs and arbitrary fetch destinations. Enforce streamed byte limits even when Content-Length is absent or false, request deadlines and image bounds before large allocation. These are required implementation controls, not features supplied by signed URLs automatically.

The worker returns a receipt only after bounded output upload completes. Ticket06 validates job/request/parent/digests/dimensions/region/object identity and current acceptance state before calling ticket04's server-only atomic attachment; a worker response alone cannot authorize attachment. Uploaded output never chooses presentation or becomes a Party Library map. A lost response after successful upload has no recoverable receipt by default; object existence or a digest cannot establish constrained lineage. Reconciliation therefore reserves another bounded **worker** invocation to reverify the existing provisional output against the retained exact source and raw candidate, through the same operation using `provisionalOutputToReverify`. It must confirm dimensions, source/candidate identities, every outside-source pixel and every selected-candidate pixel, returning a fresh receipt without uploading/overwriting an existing object. No paid provider repeat occurs. Whole-map outputs require the equivalent retained-candidate normalization comparison. This recovery operation is future implementation/proof work, not existing source behavior. An expired/cancelled job cannot attach a late output; ticket06 schedules private orphan cleanup after upload-token expiry, with its existing cleanup policy. The worker stays stateless and has no second reconciliation ledger.

## Decoder dependencies and formats

The current owned probe is builtin Node and PNG only; first proof should replay it unchanged inside Lambda's Node 24 base image. JPEG/WebP input support would be a separate approved worker dependency change. A concrete supported candidate is **sharp**: its official instructions cover Linux ARM64 binaries, require a Node-API v9 compatible runtime (for example Node ≥20.9), document JPEG/PNG/WebP support and warn to package target Linux binaries for Lambda rather than local macOS binaries. Pin the package and optional binary dependencies in an isolated worker lockfile; build for Linux ARM64/glibc and keep it outside browser dependencies. No installation or JPEG/WebP proof occurred here. [sharp installation/Lambda guidance](https://sharp.pixelplumbing.com/install/).

If adopted, explicitly set `limitInputPixels` to the accepted deployment cap, retain strict invalid-data rejection and verify decoded channel/frame count and actual dimensions. The documented default pixel limit is much larger than this proposal, and the option depends on metadata trust; it is not a replacement for independent decoded/resource validation. No implicit EXIF rotation, resizing, profile conversion or alpha premultiplication may weaken exact outside-pixel checks. [sharp constructor controls](https://sharp.pixelplumbing.com/api-constructor/). Byte-copy composition and final roundtrip comparison remain necessary; a library's general compositing support is not exact-preservation proof.

## Cost and enforcement

AWS's published on-demand **US East (N. Virginia), x86 reference** example uses $0.0000166667 per GB-second and $0.20 per million requests. Use that explicit published rate for a transparent planning calculation, **not** an asserted ARM64 tariff or London quote. [AWS Lambda pricing](https://aws.amazon.com/lambda/pricing/).

For a **60-second handler-duration planning example** at 2048 MB, handler compute plus one request is `2 × 60 × 0.0000166667 + 0.0000002 = $0.002000204`; 90 such handler runs in a 30-day month give a `$0.18001836` baseline at that reference rate, before free-tier credits. This is **not a per-invocation billing maximum**. It excludes initialization, retries, rejected invocations, reconciliation/other calls, CloudWatch, ECR storage, network transfer, Supabase storage/egress and paid image-provider charges. Obtain the chosen region/architecture's current quote before spending approval.

Lambda bills INIT time, including container-packaged functions, so billed duration can exceed handler duration. [AWS INIT billing](https://aws.amazon.com/blogs/compute/aws-lambda-standardizes-billing-for-init-phase/). For ordinary on-demand execution, initial initialization has a 10-second limit; if it does not finish, Lambda retries initialization at the first invocation using the configured function timeout. [AWS execution lifecycle](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html). Ticket06's worker budget must reserve initialization, failed/uncertain attempts and reconciliation margins, using hosted billed-duration evidence. The 60-second function timeout alone cannot establish a total billing ceiling.

Reserved concurrency 1 caps simultaneous work, **not** daily calls or cost. Ticket06 must enforce a global worker invocation allowance (including failed/uncertain attempts), tentative three/day, and the separate provider spend reservation ceiling. No nonzero ceiling is approved here. AWS Budgets notifications may lag incurred charges; they cannot serve as an exact application spending stop. [AWS Budgets timing](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html). Generation stays disabled until hosting proof, quotas and approved spending limits are accepted.

## Deployment prerequisites and smallest reversible proof

No VPC is proposed; required outbound HTTPS is limited by worker validation. Enforced network egress isolation, if demanded, needs separate network design/costs. Package a single Linux ARM64 image; do not add an AWS queue or second ledger.

AWS supplies an official Node 24 AL2023 base image at `public.ecr.aws/lambda/nodejs:24` including its runtime interface emulator (RIE), with documented ARM64 local testing and ECR deployment steps. Record the resolved image digest before later use; never treat a mutable tag as frozen evidence. [AWS Node container documentation](https://docs.aws.amazon.com/lambda/latest/dg/nodejs-image.html).
