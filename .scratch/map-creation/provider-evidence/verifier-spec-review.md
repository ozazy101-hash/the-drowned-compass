## Authority and attachment handoff

Reviewed `main/index.ts`, `worker/index.ts` and `decoder.mjs`. Preparation resolves a read-only server fixture binding and checks actual immutable source/candidate bytes against trusted sizes/digests before decode. Raw selected rows replace source RGBA, and SHA256 commits to the exact entire canonical pixel frame. Expected hash remains in server RAM, with a five-minute expiry; client responses do not supply an authoritative proof. Main strips the caller from proof construction and rejects authority headers. Finalization consumes only the private main-to-worker proof, validates request/parent/source/candidate/region/dimensions/expiry and decodes submitted PNG before comparing its actual RGBA fingerprint. Returned encoded PNG digest is computed from the submitted bytes, not caller metadata.

The hash-based staged check is authoritative content verification: browser composition is untrusted, and its claim of preservation has no authority. Whole decoded-frame equality binds outside source pixels and selected candidate pixels without server PNG encoding. Accepted proof still depends on exact source/candidate decoder semantics and trusted bindings; digest integrity alone cannot establish registration.

The README explicitly hands ticket06 the server-only prepared proof in its **sole** durable request/job intent record, bound to request/job/origin, saved parent/revision, source/candidate immutable object identities and digests, canonical dimensions, region and proof/verifier version. Final receipt must bind encoded PNG digest/size/MIME and those identities. Attachment/recovery must independently re-read/reverify the **same immutable stored object** against the **same authoritative proof/binding**, check current session/job cancellation/expiry and parent revision, and reject replaced bytes or stale cached receipts. Verification does not select presentation or self-authorize inherited registration. These are required implementation checks, not already-tested storage or SQL claims.
