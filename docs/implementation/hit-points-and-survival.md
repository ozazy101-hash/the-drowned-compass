# Hit Points and survival

Ticket 07 adds `PartyData.updateSurvival(slotId, command, expectedVersion, maximumVersion)`. The survival domain module owns command validation, damage and healing calculations, direct corrections, recent-action undo, downed labels, and version-aware snapshot merging. `SurvivalSection` owns drafts and save feedback; the Character Page composes it in Overview and Combat. Party cards read accepted survival state.

Current Hit Points begin as unknown for existing and newly claimed records. Players explicitly correct them before applying damage or healing. Damage consumes Temporary Hit Points first and floors current Hit Points at zero. Healing caps current Hit Points to the accepted maximum without altering Temporary Hit Points. Direct current and temporary corrections accept whole numbers from 0 to 9999; current corrections can exceed maximum for table rulings. Maximum Hit Points retain their existing independently versioned Overview editor.

Death-save successes and failures are independently editable counters within the survival record, each bounded to 0–3. Heroic Inspiration and manual Unconscious state are editable flags. Current HP of zero adds a downed/unconscious label without modifying a player's manual flag; three successes label a downed character stable, and three failures display an explicit failure label. Healing and corrections leave manually tracked death saves and flags under player control. This module does not adjudicate death, instant death, or other rule interactions.

Each accepted survival command increments one survival version. Damage, healing, and current/temporary corrections replace a shared one-action undo snapshot containing only current and temporary HP. Undo restores that snapshot, clears it, and preserves death saves, Inspiration, manual Unconscious state, and all other Character Record information. The latest action is visible after navigation/reload and may be undone by either role. A stale expected survival version rejects the entire action. Maximum-HP version changes invalidate history and reject actions calculated from a stale maximum. Undo cannot be repeated or overwrite another accepted HP action; the UI asks the editor to review current values after a conflict. Maximum corrections are not included in this health-action history.

The local adapter serializes shared localStorage writes using the existing Party write Web Lock. The test transport applies the same transition module under its serialized request handler. Supabase stores one independently addressable survival record per Character Slot. Browser roles can read it only through Party membership RLS and can write only through the conditional RPC. The RPC checks membership and claim, locks the Character Slot, validates command inputs, reads the accepted maximum and its version, applies the transition, and increments the survival version atomically. Realtime events and reconnect reloads deliver accepted state. Monotonic survival merging prevents delayed reads from rolling the Character Page back.

The forward migration must be approved and applied before releasing this frontend to the hosted Supabase backend. All development database checks use rollback-only fixtures. This ticket does not apply hosted migrations or deploy the frontend.
